# 게임 1.0.33 디버깅 기록

2026-09-30, 설치된 Windows 게임에서 Computer Use로 확인한 결과입니다. 게임 DLL/에셋이나 다른 모드의 코드는 저장소에 포함하지 않았습니다.

## 수정된 문제

- Unity 6의 Input System 전용 환경에서 legacy `Input.GetKeyDown`이 예외를 발생시켰습니다. IMGUI 키 이벤트로 교체했으며 키를 놓기 전 반복 입력은 래치로 무시합니다. Windows 키 상태 조회는 래치 해제에만 사용하며 게임 행동을 시작하지 않습니다.
- 가져오기 창에 포커스가 있으면 키 이벤트가 `GUI.Window` 콜백 안으로 전달됩니다. 바깥 `OnGUI`뿐 아니라 두 창의 콜백에서도 같은 래치 기반 처리를 수행합니다.
- Wiki 테이블 ID와 게임 ID가 달랐습니다. 예: `blue_claws`는 Wiki ID 181이 아닌 게임 ID 1145, 최종 무기 `eternal_snow_silence`는 게임 ID 420입니다. 카테고리 별칭과 Miracle ID 대소문자도 달랐습니다. 게임 엔티티를 한 번씩 읽어 정확한 ID/메타데이터를 검사하도록 수정했습니다.
- 무기 부모는 사용되지 않는 `enhanceFromId`가 아닌 활성 `standardEnhancements` 관계에서 역방향으로 찾습니다. 여러 부모와 순환은 검증 실패로 처리합니다.
- Mono HTTP 초기 작업은 백그라운드로 분리하고 Unity 객체 검사만 메인 스레드에서 수행합니다.
- 임의의 revision 변화는 요청 성공으로 보지 않습니다. 보상 획득, 목표 무기/나무 뿌리 변화, 리롤 후보 변화 등 해당 동작의 결과를 기다립니다. 이것은 관찰 기반 확인이며 명시적인 서버 ACK 훅은 아닙니다.
- 검토 창이 열려 있거나 가져오기/기존 요청이 진행 중이면 F8을 실행하지 않습니다. 검증되지 않은 바인딩은 자동 행동을 허용하지 않습니다.
- 빈 슬롯으로 옮기는 기존 아티팩트에 신규 획득용 `CanAddItemAtPositionForSwap` 검사를 적용해 유일 효과 아이템이 거절되는 오류가 있었습니다. 이동은 같은 소유 인스턴스/엔티티와 빈 목적지, 일반 인벤토리 모드, 유효 슬롯/비활성 슬롯 여부를 재검증하고 기존 `Swap` 요청 경로만 사용하도록 수정했습니다.

## 실제 확인 범위

- 기존 저장 슬롯으로 실제 런 진입 및 F6 빌드 가져오기.
- 공개 예제 UUID `c4fa31fc-5b95-4e04-a08b-dfb752f3bf21`: 5개 구역, 최종 바인딩 47개 중 Verified 46개, MetadataMismatch 1개(`ice_snow`, Wiki Uncommon / 게임 Rare). 안전 검증을 완화하지 않았습니다.
- 초기화 완료 후 F8을 각각 눌렀을 때 미활성 빌드 실행 차단 로그.
- 정상 Steam 재실행 후 실제 런의 F6 열기/닫기/다시 열기 및 가져오기 완료. 최종 창 내부 입력 수정본은 메인 메뉴에서 입력칸 포커스 상태의 F6 닫기와 F8 두 입력의 개별 차단 로그를 재확인했습니다.
- 모든 구역이 미분류 상태일 때 활성화 거절.
- Release 빌드(경고/오류 0)와 자동 테스트 78개 통과.
- 승인된 분류(첫 두 구역 필수, 나머지 추천)를 재로딩 후 복원하고, 실제 아이템 선택창의 5개 아이템/리롤 후보 및 로컬 소유권을 코드로 확인했습니다.
- 상시 아이템 캡션을 제거하고 추천 리롤의 이중 프레임/작은 F8 표시, 주사위 4→3 및 나무 뿌리 위험 경고를 화면으로 확인했습니다. 현재 후보에는 빌드 목표가 없으므로 금색/하늘색 목표 프레임 분류는 자동 테스트 범위입니다.
- 게임의 `PIXEL_SMALL` TextMeshPro 폰트 자산을 그대로 참조합니다. 원본 TTF가 없는 폰트이므로 인게임 표시는 IMGUI가 아닌 수동 입력 비수신 Canvas/TMP로 구현했습니다. F6 IMGUI 검토 창은 별도 폰트 폴백을 유지합니다.
- 슬롯 (0,0)의 반투명 고스트는 10초짜리 **비실행 표시 검증**으로 확인했습니다. 실제 개선 결과는 당시 0개였으므로 이 표시를 배치 최적화 성공으로 세지 않습니다.
- F7 숨김/복원과 3회 연속 읽기 전용 검사에서 돈/주사위/인벤토리 불변을 확인했습니다. 마우스 오버의 legacy Input 예외도 IMGUI mousePosition으로 수정하고 비용 경고 표시를 재확인했습니다.

## 실제 F8 동작 검증 (v0.1.2 수정본)

각 동작은 실제 게임 창에 F8을 한 번 입력한 뒤 읽기 전용 런타임 스냅샷, 화면과 동작 로그로 확인했습니다. 테스트 인터페이스로 소비/이동 명령을 실행하거나 게임 저장 데이터/아이템을 직접 변경하지 않았습니다.

| 시나리오 | 실제 관찰 | 결과 |
| --- | --- | --- |
| 유료 아이템 리롤 | F8 한 입력, `Reroll` 요청 한 건, 공유 주사위 4→3, 돈 420 유지, 후보 변경 | 통과 |
| 필수 아티팩트 선택 | F8 한 입력, `Select` 요청 한 건, 크리톤의 인장 인스턴스 추가, 선택창 닫힘, 확인된 획득 0→1 | 통과 |
| 기존 유일 효과 아티팩트 빈 슬롯 이동 | 네이티브 클릭으로 악보 '바람'을 (5,0)→(0,0)으로 준비한 후 F8 한 입력, `Move` 한 건, 같은 인스턴스가 (5,0)으로 복귀, 돈 340/주사위 4 유지, 획득 횟수 불변 | 통과 |
| 회전 불가 석판의 네이티브 입력 | 동시성의 회전 불가 표시, 우클릭 후 회전 0과 칸별 효과/돈/주사위 불변 | 통과 (음성 테스트만) |
| F8 석판 회전 성공 | F8 회전 런타임 경로 미구현. 보유 석판 3개의 원본 `isRotatable` 값도 모두 false | 미검증/미구현 |
| 금전 구매·지혜 10 병합 | 해당 실제 화면/상태에서 실행하지 않음 | 미검증 |

회전 불가 입력이나 순수 솔버 회전 테스트를 실제 F8 회전 성공으로 세지 않습니다. `Succeeded` 로그는 해당 동작의 결과를 관찰했다는 뜻이며 명시적인 서버 ACK 수신 증거가 아닙니다.

재시작으로 게임이 이전 체크포인트(돈 340/주사위 4, 크리톤 없음)를 복원했지만 런 ID가 같아 모드 획득 기록은 1회로 남는 제한도 발견했습니다. 테스트로 생긴 차이는 F6의 보정 버튼 한 번으로 사용자 보정 -1, 유효 획득 0회로 되돌렸습니다. 기록의 자동 체크포인트 동기화는 아직 구현되지 않았습니다. 현재 인벤토리 수만으로 병합/버린 아이템의 과거 획득을 추론해 기록을 지우지 않습니다.

사용자 요청에 따라 멀티플레이 실게임은 범위에서 제외했습니다. 현재 석판 기준의 아이템 고스트/빈 슬롯 이동만 연결했고, 석판 회전·조건부 효과 최적화·점유 슬롯 교환은 수동입니다. 상점 획득 카운트 및 보상 포기/변환 연결도 미완료입니다. 가져오기 창은 네이티브 입력을 차단하지 않으므로 안전한 장소에서 검토하세요.

## 실제 F8 석판 회전 (v0.1.3)

사용자가 체크포인트에 저장한 '전이' 석판(게임 ID 2004, 위치 (2,2))을 재시작 후 복원해 검증했습니다. 원본 회전 플래그뿐 아니라 `DungeonManager.IsTabletRotatable`의 실제 판정(런 중 회전 권한 변경 포함)을 확인합니다. 커서 아래의 로컬 인벤토리 석판에만 회전 프레임/F8 안내를 표시하며, 이 동작은 **사용자가 지정한 회전이지 자동 최적화 결과가 아닙니다**.

- 네 번의 별도 F8 입력으로 회전값 2→3→0→1→2. 각 입력마다 `Rotate` 요청 한 건과 관찰 기반 `Succeeded` 한 건.
- 첫 입력 후 (2,0) 레벨 -1→+1, (5,2) 레벨 5→3. 네 번째 입력 후 모든 칸 레벨과 석판 방향이 시작 상태로 복원됨.
- 전체 동작에서 돈 500/공유 주사위 1, 아이템 인스턴스/위치 및 다른 석판의 방향은 불변.
- F7 숨김 상태의 F8은 요청을 보내지 않음. 회전 불가 '동시성' 석판 위의 F8도 회전 요청을 추가하지 않으며 전체 회전값/자원 유지.
- 회전 프레임은 게임의 TMP 폰트를 참조하고 마우스를 가로채지 않음. 안내 문구는 해당 폰트로 크기를 계산하며 결과를 캐시함.
- 네이티브 `UI_CharacterStatusPanel.OnTabletRotate` → `GridInventory.DoClickAction` 요청 경로 사용. `StoneTablet.Rotate` 직접 호출이나 회전 필드/게임 저장 파일 변경 없음.
- 인스턴스/엔티티/위치/각도, 같은 소유 인벤토리, 일반 인벤토리 모드, 보이는 슬롯/포인터/실제 회전 권한을 직전에 다시 검증. 후보 토큰과 revision에 석판 상태가 포함되며 정확히 한 단계의 동일 석판 회전만 성공으로 관찰.
- Release 빌드 경고/오류 0, 자동 테스트 84개 통과. 자동 배치 탐색 및 조건부 효과 최적화의 실게임 성공을 의미하지 않음.

## 통합 자동 배치 (v0.1.4)

- 게임의 읽기 전용 쿼리 파서로 허용 위치/회전의 효과와 조건을 캡처하며, 현재 레벨/비활성/조건 무시 맵을 정확히 재현할 수 있을 때만 계산합니다. 제단 강화는 슬롯이 아니라 해당 인스턴스와 함께 이동합니다. 고정 각인은 이동/회전 후보에 넣지 않습니다.
- 취소 가능한 백그라운드 제한 탐색과 공통 슬롯 최소 비용 매칭을 연결했습니다. 최대 6패스/6,000평가이며 전역 최적해 증명이 아닙니다. 일반 카테고리 콤보 수량은 보유 인스턴스를 그대로 유지하므로 일정합니다. 미지원 특수 사전 콜백/배열 보너스는 자동 배치를 중단합니다.
- 실제 싱글플레이 보드에서 석판 1개 이동 + 아티팩트 2개 이동을 별도 F8 세 번으로 수행했습니다. 각각 요청 1건과 관찰 기반 성공 1건이었고, 추천 목표 합산 레벨이 예측한 12→14가 됐습니다. 중간 상태가 최종 상태보다 나빠도 예상한 한 단계만 관찰되면 최종 계획을 유지합니다.
- 별도 회전 필요 상태에서 솔버가 270°→0°를 선택했습니다. 커서를 인벤토리 밖에 두고 F8을 한 번 입력해 같은 석판의 회전과 칸 효과 복원을 확인했습니다. 수동 포인터 회전 테스트가 아니라 `opt:rotate` 요청이었습니다.
- 돈 500/공유 주사위 1은 유지됐고, 완료 후 일반 F8 추가 입력은 요청을 보내지 않았습니다. 3회 연속 읽기 전용 스모크 검사도 통과했습니다. 인게임 강조는 두꺼운 테두리/어두운 대비선/밝은 모서리이고 네이티브 TMP 폰트·입력 비수신 Canvas를 유지합니다.
- 자동 테스트 102개 통과, Release 빌드 경고/오류 0. 조건부/고정 각인/배율/이웃/중복/점유 칸 교환/취소/예산은 순수 모델 테스트이며, 이 특수 상태들을 실제 런에서 전부 검증했다고 표시하지 않습니다.
- 안정 인벤토리 구간에서 스냅샷 평균 약 1ms, p95 약 1.2–1.4ms, 포커스 상태 약 144 FPS를 관찰했습니다. 최초 위치별 네이티브 파싱은 약 3ms씩 분할하고 캐시합니다. 단일 네이티브 호출/첫 JIT 비용까지 엄격한 3ms 이하를 보장하는 것은 아닙니다.

## 성능 측정 이력

기존 메인 스레드 스냅샷은 안정 구간 평균 약 205–215ms, p95 약 267ms였습니다. 전체 Unity 리소스 스캔을 네이티브 UI/상호작용 등록부로 대체하고, 타입/멤버 메타데이터만 캐시했습니다. 소유권·후보·비용은 F8 직전 다시 읽습니다. 계산에는 Unity 객체를 전달하지 않습니다.

최종 아이템 선택창의 안정 구간은 평균 약 0.6ms, p95 약 0.7–0.8ms, 포커스 상태 약 144 FPS였습니다. 초기화/재로딩 첫 스냅샷 약 76–78ms는 별도입니다. 이는 해당 PC/장면의 진단값이며 모든 장면의 FPS 보장은 아닙니다. 측정/진단은 일반 배포의 기본값에서 꺼집니다.

## v0.1.5 패드 입력

- `ControlsChangeHandler.Current.PlayerInput.currentControlScheme`을 읽어 게임의 모드 전환을 따릅니다. `PlayerInput.devices`에 연결된 Gamepad 한 개만 허용하며 전역 `Gamepad.current`는 사용하지 않습니다. View/Back + 방향키 ↑/←/→가 검토/표시/단일 확인의 기본입니다.
- 길게 누르기, 확인 방향키를 누른 채 Modifier만 다시 누르기, 모드 변경, 연결 해제, 장치 변경, 포커스 복귀에서 추가 행동이 시작되지 않는 테스트를 포함해 115개 자동 테스트가 통과했습니다. API 모형 테스트는 게임 입력 주입이 아닙니다.
- 패드 검토 창은 페이지와 버튼 포커스로 조작합니다. 검토 중에만 네이티브 `InputSystemUIInputModule.Process`/`UIInputModule.Update` 입력을 분리하며 종료 입력의 한 프레임도 보호합니다. 훅 설치 실패 시 패드 검토 제출을 금지합니다. 정상 게임 화면에서 네이티브 입력을 막지 않습니다.
- 실제 1.0.33 런에서 Keyboard&Mouse, 로컬 패드 0개, 모달 훅 설치 성공과 승인된 빌드 복원/프레임/고스트/게임 폰트의 읽기 전용 회귀 검사가 통과했습니다. 10초 비실행 패드 창 미리보기에서 분류/횟수/우선순위/활성화 버튼 배치를 확인했고 돈 500·주사위 1은 유지됐습니다.
- 실제 패드가 없어 물리 입력, Steam Input 버튼 매핑, 패드 제출의 뒤쪽 UI 동시 실행 여부는 미검증입니다. 게임/Steam 재매핑으로 View와 방향키의 네이티브 행동이 겹치면 설정 Modifier를 바꾸세요. 직접 문자열 입력은 키보드 모드, 패드에서는 클립보드 붙여넣기를 사용합니다.

## v0.1.6 입력·인챈트·종료 수정 (Computer Use 미사용)

- 가져오기 기본 키 F9, 기존 F6 기본값의 일회 이전, 사용자 지정 키 보존. 실제 설치 설정에서 `ImportWindow = F9`, `ImportF9MigrationApplied = true`를 확인했습니다.
- 모든 입력 모드의 검토 패널을 모달화했습니다. 네이티브 UI Process/취소 처리, 인벤토리 Update, InputAction의 버튼 폴링을 보호하고 패널 밖 IMGUI 클릭/스크롤을 소비합니다. 닫는 입력을 놓은 뒤 두 프레임까지 보호하며, 현재 게임 DLL에서 확인한 `ResetPointers`로 누적 포인터 상태를 지웁니다. 네이티브 포커스는 유효한 객체에 한해 복원합니다. 다른 모드의 독자적인 원시 입력은 통제하지 않습니다.
- 인챈트 화면의 목표 인스턴스마다 강화 순위를 표시합니다. 필수/빌드 우선/현재 개선/낮은 강화 횟수 순서, 네이티브 최대 강화 횟수, 중복 인스턴스와 불명 상태를 검증했습니다. 강화 자동 실행은 없고 인챈트 중 Move/Rotate 추천과 고스트를 중단합니다.
- 136개 자동 테스트 통과, Release 빌드 경고/오류 0. 추가 테스트는 순수 모달 상태·F9 이전·강화 순위·종료 취소·타이틀 종료 안전 조건입니다. 신규 패널 클릭 관통과 인챈트 렌더링의 실게임 상호작용은 미검증입니다.
- PID 47392의 기존 두 덤프를 Windows CDB와 Unity 공식 심볼로 로컬 분석했습니다. `CleanupEngine → CleanupModule_Accessibility → UiaDisconnectAllProviders → COM message pump → PlayerMainWndProc → win::NewInput::Activate+0x92`, 이미 null인 입력 싱글턴 역참조입니다. 첫 덤프는 `c0000005`, 두 번째는 `c000041d`. 이는 모드의 관리 예외나 폰트 해제라고 확정할 수 없는 Unity 네이티브 종료 순서 문제입니다. 덤프/게임 바이너리는 저장소에 포함하지 않습니다.
- Microsoft의 [UIA 종료 정리 지침](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcoreapi/nf-uiautomationcoreapi-uiadisconnectallproviders)에 따라 Input System이 살아 있는 OnApplicationQuit에서 접근성 제공자를 먼저 끊습니다. 현재 프로세스 창에서 정리 호출 중에만 WM_GETOBJECT 재등록을 방지하고 즉시 훅을 해제합니다. 프로세스 강제 종료, 크래시 핸들러 비활성화, 엔진 바이너리 패치는 없습니다. 동기 SendMessage 처리 중이면 안전하게 건너뛰고 로그를 남깁니다.

## 로그와 프로세스

`BepInEx/LogOutput.log`는 UTF-8로 읽습니다. `loaded ... PID=`와 현재 게임 PID 및 로그 수정 시각을 함께 비교하세요. 게임 실행 직후 Steam이 프로세스를 교체하면 첫 프로세스의 정상 로드 로그만 남을 수 있습니다. 화면에 보이는 프로세스가 같은지 반드시 확인합니다.

직접 실행 디버깅에서는 게임 루트에 임시 `steam_appid.txt`(2436940)를 사용했습니다. 이는 Steam 재실행 경로를 피하기 위한 개발용 파일이며 배포 패키지에는 넣지 않습니다. 해당 파일은 제거했고 로더 DLL과 설정도 원복했습니다.

임시 파일 제거 후 기존 Steam 프로세스에서 실행했을 때는 실제 런에서도 로더가 시작되지 않았습니다. Steam을 메뉴로 완전히 종료하고 다시 시작한 뒤 플레이 버튼으로 실행하자 같은 기본 설정에서 로더와 플러그인이 정상 로드됐습니다(PID 37320). Steam이 Doorstop 초기화 환경변수를 전달하는 [공식 저장소의 알려진 사례](https://github.com/NeighTools/UnityDoorstop/issues/34)와 일치하는 증상입니다. 이 환경의 직접 원인 변수는 읽지 않았으므로 환경변수 전달은 추론입니다. 영구적인 disable 무시 설정은 적용하지 않았습니다.

## 카탈로그 재검증

설정 `BepInEx/config/io.github.sephiria.build-overlay.cfg`의 `[Debug] ExportRuntimeCatalog = true`를 켜고 게임을 재시작한 뒤 F6 가져오기/매핑 재검증을 실행하면 `%LOCALAPPDATA%/SephiriaBuildOverlay/catalog-observed-1.0.33.json`에 엔티티 메타데이터만 기록합니다. 평소에는 false로 둡니다.

```powershell
.\tools\ReconcileCatalog.ps1 -SnapshotPath '<관찰 JSON 경로>'
dotnet test SephiriaBuildOverlay.sln -c Release
```

Reconcile은 같은 버전의 한국어 이름 및 아티팩트 희귀도/카테고리로 유일하게 연결되는 ID만 채택합니다. 모호하거나 메타데이터가 다른 항목은 미해결 키로 유지합니다. 무기 티어/부모 기대값은 보존하므로 런타임 검사가 필요합니다. Wiki를 다시 생성할 때는 별도 임시 OutputPath를 사용하고 관찰 데이터와 비교하세요.

Codex Apps에서 시작한 프로세스는 Windows 패키지 파일 리디렉션으로 위 경로가 `OpenAI.Codex_.../LocalCache/Local/SephiriaBuildOverlay` 아래에 생길 수 있습니다. 로그의 논리 경로만 보고 캐시가 없다고 판단하지 마세요.
